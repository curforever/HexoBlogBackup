做 VR 优化时，容易先关注“某个数字有没有变好”：帧时间变低、缓存命中率变高。但系统接起来之后，真正要回答的是：画面质量是否保住了？用户需要的内容是否及时到达？缓存决策本身又增加了多少处理开销？

这篇根据我的终版毕业论文整理，只讲问题、取舍和实验口径。图表复用论文正文；数字来自论文汇总，本轮没有重新运行实验。

## 先看系统中两个优化位置

![端边协同系统总体架构，原论文图 5-1](/images/research/system-architecture.png)

| 位置 | 优化想法 | 需要保住什么 |
| :--- | :--- | :--- |
| 终端侧 | 当前任务不需要的细节少算一点 | 用户关心区域的画质，参数变化的连续性 |
| 边缘侧 | 多人共同使用的对象块尽量复用 | 缓存容量、决策成本和响应节奏 |
| 两端之间 | 状态与决策及时交换 | 通信与处理链路的可观察性 |

这对应论文的三个阶段：任务感知中心凹渲染、多用户共享视场缓存，以及端边集成系统。

## 阅读文字和追踪目标，应该用同一套参数吗？

![不同眼动任务的渲染效果，原论文图 3-6](/images/research/task-rendering.png)

中心凹渲染通常把更多质量放在注视中心，外围降低分辨率。我的研究进一步从一段头动与眼动序列识别当前任务，再调整高质量区域、过渡区域与外围质量。

为什么需要任务信息？因为同一个注视位置，可能对应读文字、跟随移动目标或搜索场景物体。任务不同，对细节、范围和连续性的需求也不同。

| 渲染策略 | 片段平均帧时间 | 平均片段超预算比例 |
| :--- | ---: | ---: |
| 全分辨率 | 10.14 ± 2.99 ms | 33.42% |
| TAFR | 5.40 ± 2.97 ms | 4.81% |

来源：终版论文表 3.7。以场景—路径片段为单位，先计算片段统计，再取平均。相对全分辨率加速比为 1.88×，但这是渲染实验的结果，不是完整 VR 系统的端到端加速比；图像质量仍需结合多项指标和具体场景判断。

## 缓存命中更高，系统就一定更快吗？

![系统实验缓存与共享命中率，原论文图 5-10](/images/research/system-cache.png)

缓存复用能减少重复处理，但识别共享关系、形成用户群组、推理与更新缓存状态也会消耗时间。因此，需要同时看收益和处理成本。

| 指标 | 它能说明什么 | 它不能独自说明什么 |
| :--- | :--- | :--- |
| 缓存命中率 | 当前请求中已有内容被复用的程度 | 画面质量和完整用户响应时间 |
| 共享命中率 | 跨用户共享内容的复用情况 | 对所有新用户和新场景都有效 |
| 边缘处理代理时延 | 请求进入边缘服务到响应生成的耗时 | 网络往返和头显 Motion-to-Photon 时延 |

第五章六个成对条件中，SCOPE-DDQN 相对 LRU 的缓存命中率平均相对增益为 <strong>22.08%</strong>，共享命中率为 <strong>42.78%</strong>。这两个数是各条件相对增益的平均值，不是百分点差值。

举一个可以直接核算的条件：20 用户短时实验，命中率从 44.37% 到 58.47%，增加 14.10 个百分点；相对增益为 `14.10 / 44.37 ≈ 31.78%`。

## 长时运行的图，要看走势，也要看口径

![60 用户、30 分钟的窗口级结果，原论文图 5-12](/images/research/long-run.png)

这张图的窗口级命中率均值是 57.16%，边缘处理代理时延均值约 153.44 ms。需要注意三点：

1. 横轴是时间窗口编号，不能直接读成秒或毫秒。
2. 代理时延不是完整头显端到端时延。
3. 60 用户指可控仿真请求负载；真实头显接入验证的是行为采集、渲染与通信链路，并不代表 60 位真人同时戴头显体验。

## 我希望以后继续检查的取舍

| 如果追求这个目标 | 同时检查这个代价 |
| :--- | :--- |
| 更高画质 | 渲染开销是否超出预算 |
| 更高复用率 | 群组识别和策略决策是否增加处理成本 |
| 更快响应 | 是否降低了用户真正需要的画面质量 |
| 更稳定的均值 | 高分位表现、窗口波动与不同用户是否均衡 |

把三个阶段接成系统后，我更重视清楚定义指标：优化了哪个环节、在哪组条件下观察到收益、还有哪些成本没被测量。这样，数字才可以用来指导下一次设计。
